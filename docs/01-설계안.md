## 1. 기술 결정

### 1.1 결정: Tauri 2 + React 18 + TypeScript + Rust + SQLite(rusqlite)

| 검토 대상 | 판단 |
|---|---|
| **Tauri 2 + React + Rust + SQLite** | **채택.** 이 PC에서 같은 구성으로 5개 프로그램(보결 배정·방과후 매니저·문서 통합·견적서 관리·업무 도우미봇)을 만들어 배포까지 마쳤다. 마이그레이션 러너·백업/복원·업데이터·GitHub Actions 릴리스 절차를 그대로 가져올 수 있고, 필요한 크레이트(rusqlite bundled, calamine, rust_xlsxwriter, tauri-plugin-dialog)가 모두 로컬 캐시에 있다. |
| Electron + better-sqlite3 | 설치 파일이 150MB 이상으로 커지고, 네이티브 모듈(sqlite) 빌드가 Windows 업데이트마다 깨지기 쉽다. 이점이 없다. |
| .NET WPF/WinUI + SQLite | Windows 전용으로는 적합하지만 기존 자산(디자인 토큰·릴리스 파이프라인·서명 키 운용)을 하나도 못 쓴다. |
| Python + PySide | 배포(PyInstaller) 크기와 바이러스 오탐 문제가 크다. |

**Rust에 두는 것과 화면(TS)에 두는 것의 경계**

- 데이터 정규화(생년월일·연락처·주소), 형제 판정, 번호 재정렬, 진급 계산, Excel 읽기/쓰기, 통계 집계는 **모두 Rust(`domain`, `repo`)** 에 둔다. 이유: 단위 테스트가 쉽고, 1,000명 이상 처리 시 UI 스레드를 막지 않으며, 화면을 바꿔도 규칙이 흔들리지 않는다.
- 화면은 **표시와 사용자 선택**만 맡는다. 화면에서 계산하는 값은 정렬·필터 표시 정도이고, 저장되는 값은 항상 Rust가 만든다.
- 대량 처리(가져오기·학년도 전환)는 Rust 별도 스레드에서 실행하고, 진행률을 Tauri 이벤트로 화면에 보낸다(§7.2).

### 1.2 데이터 위치와 개인정보

- DB: `%APPDATA%\kr.school.studentroster\studentroster.db` (SQLite, WAL 모드). 백업은 `backups\`, 내보내기는 `exports\`.
- 네트워크 통신은 **업데이트 확인(GitHub Releases) 하나만** 한다. 학생 자료는 어떤 경로로도 밖으로 나가지 않는다. 로그에도 학생 이름·연락처를 남기지 않는다.
- 파일 자체는 암호화하지 않는다(§10-9 참조). 대신 사용자 계정 폴더에 두고, 설정 화면에 "이 PC의 Windows 계정 암호와 BitLocker 사용"을 안내한다.

## 2. 요구사항 분석 — 도메인 개념 정리

요구사항 25개 항목을 아래 개념으로 압축했습니다. 이 개념이 데이터 모델과 화면 구조의 뼈대입니다.

| 개념 | 설명 | 요구사항 근거 |
|---|---|---|
| **학생(Student)** | 사람 한 명. 이름·성별·생년월일·주소·보호자·비고. 학년도가 바뀌어도 한 행. | §3 "기본정보와 학년도별 상태 분리" |
| **학적(Enrollment)** | 학생 × 학년도. 학년·반·번호·상태(재학/전입/전출)와 전입일·전출일. 학년도마다 한 행. | §3, §13~16 |
| **졸업(Graduation)** | 학생이 어느 학년도에 졸업했는지. 학적을 덮어쓰지 않고 별도 기록. | §16, §18 |
| **주소 분류(AddressCategory)** | 1단지·2단지·주택·기타 같은 통계용 분류. 학교마다 다르므로 사용자가 목록을 관리. | §7, §19 |
| **주소 규칙(AddressRule)** | "○○로 123 → 5단지" 같은 판정 규칙. 자동 판정·사용자 규칙·직접 지정을 구분. | §7 |
| **형제 연결(SiblingLink)** | 학생 ID 쌍. 후보/확정/거부 상태와 일치·불일치 항목. 표시는 현재 학적으로 그때그때 만든다. | §8, §9 |
| **확인 필요(Issue)** | 학생에게 붙는 "나중에 봐야 할 것". 종류·메시지·근거·처리 상태. 입력을 막지 않는 장치. | §10~12, §24-1 |
| **가져오기(Import)** | Excel 한 번 읽어 들인 기록과 결과 요약. | §10~11 |
| **학년도 전환(YearTransition)** | 이전 학년도 학적 + 반배정 자료 + 신입생 자료 → 다음 학년도 학적 생성 기록. | §16~17 |
| **출력(Export)** | 열 선택 명단·외부 시스템 양식. 데이터 모델과 분리된 변환 모듈. | §20~21 |

### 2.1 요구사항을 그대로 구현하면 문제가 되는 지점 (설계로 해결)

1. **"학생 상태 = 재학/전입/전출/졸업" 하나의 열** → 졸업은 학년도별 상태가 아니라 학생 인생에 한 번 있는 사건이다. 학적 상태(재학·전입·전출)와 졸업 기록을 분리하고, 화면의 상태 pill은 두 가지를 합쳐 계산한다. 이렇게 하면 2026학년도 명단을 나중에 열어도 6학년이 그해 모습(재학)으로 보이고, 졸업생 화면은 졸업 기록으로 조회한다.
2. **"본교 형제 항목에 `1-나리 홍길동`을 자동 입력"** → 문자열을 저장하면 진급 때 깨진다(요구사항 §8 후반도 같은 걱정). 학생 ID 연결만 저장하고 문자열은 조회 시 만든다. 사용자 수정은 "연결 추가·해제·거부"로 제공한다. 자유 텍스트가 꼭 필요하면(예: 타교 형제) 비고란을 쓴다.
3. **"확인 필요"를 학생 행의 플래그로 두면** 종류가 늘 때마다 열이 늘고, 하나의 학생에 여러 문제가 있을 때 표현이 안 된다 → 별도 `issues` 표. 학생명단의 "확인 필요" 표시는 열린 issue 개수로 계산한다.
4. **주소 분류에 "자동 판정" 규칙을 코드에 박으면** 세종시 외 학교나 새 단지가 생길 때 업데이트가 필요하다 → 자동 판정은 "주소 문자열에서 `N단지`를 찾는" 최소 규칙만 코드에 두고, 나머지는 모두 사용자 규칙 데이터로 둔다.
5. **번호 재정렬을 화면(TS)에서 계산하면** 미리보기와 실제 적용이 어긋날 수 있다 → Rust 함수 하나가 미리보기(변경 목록)를 만들고, 적용은 그 목록을 그대로 저장한다.

## 3. 데이터 모델

### 3.1 표 목록

```
settings            key-value (학교명 등)
school_years        학년도 목록, 현재 학년도 표시
address_categories  주소 분류 목록 (사용자 관리, 기본: 주택·기타)
address_rules       주소 → 분류 규칙 (ROAD/COMPLEX/CONTAINS)
students            학생 기본정보 (원본 + 정규화 값 + 판정 근거)
enrollments         학년도별 학적 — **현재 상태** (학년·반·번호·상태)
enrollment_events   학적 이동 이력 — 사건을 덧붙이기만 한다 (§11.1)
graduations         졸업 기록 (학생 1행)
sibling_links       형제 연결 (후보/확정/거부)
issues              확인 필요 항목
imports             가져오기 기록
year_transitions    학년도 전환 기록
renumber_ops        번호 재정렬 작업 기록 (작업 1건 = 1행)
```

### 3.2 `students` — 원본과 정리값을 나란히 둔다

| 열 | 내용 |
|---|---|
| `name`, `gender`(M/F/NULL) | |
| `birth_raw` / `birth_date` | 입력 원문 그대로 / `YYYY-MM-DD`. 변환 실패면 `birth_date`는 NULL이고 BIRTH issue가 열린다 |
| `address_raw` / `address_norm` / `address_road` | 원문 / 정리본(검색·규칙 맞춤) / 뽑아낸 `도로명 건물번호` |
| `address_category_id`, `address_source`(NONE/AUTO/RULE/MANUAL/CONFLICT), `address_rule_id` | 분류값 + **어떻게 정해졌는지** + 어느 규칙이 적용됐는지. MANUAL 은 자동 재분류가 건드리지 않고, CONFLICT 는 규칙이 부딪혀 정하지 못한 상태다 |
| `father_name`, `mother_name` | |
| `father_phone` / `father_phone_digits` (모·주보호자 동일) | 표시용 `010-1234-5678` / 검색·비교용 숫자만 `01012345678` |
| `note` | 비고 |

연락처를 두 열로 두는 이유: 요구사항 §4·§8의 "표시 문자 제거 후 검색·비교"를 SQL `LIKE '%1234%'` 한 번으로 처리하고, 화면에는 항상 정리된 형식을 보여주기 위해서다.

### 3.3 `enrollments` — 학년도별 한 행

| 열 | 내용 |
|---|---|
| `student_id`, `school_year` | UNIQUE. 한 학년도에 한 학적 |
| `grade`(1~6), `class_name`(TEXT), `class_no`(NULL 허용) | 반은 `'1'`, `'가람'` 처럼 텍스트. NULL 반 = 반배정 미정(전환 때 자료가 없던 학생) |
| `status` | `ENROLLED`(재학) / `TRANSFER_IN`(전입) / `TRANSFER_OUT`(전출) |
| `transfer_in_date`, `transfer_out_date`, `transfer_out_to`, `transfer_out_note` | **가장 최근 값의 사본.** 이동 이력의 원본은 `enrollment_events` 다 (§11.1). 돌아오면 전출 칸을 비운다 — 지금 가장 최근 일은 들어온 것이기 때문이다 |

**현재 재학생** = 현재 학년도 학적 중 `status IN ('ENROLLED','TRANSFER_IN')`. 전입생은 재학생 명단에 포함된다(§13).

반 정렬 규칙: 숫자로 읽히면 숫자 순, 아니면 가나다 순. 학교가 반 순서를 따로 정하고 싶으면 설정에서 학년별 반 순서를 지정할 수 있게 확장 가능(§10-3).

### 3.4 `graduations`
`student_id`(PK), `school_year`(졸업한 학년도 = 6학년이었던 해), `graduated_at`, `note`. 졸업생 화면은 이 표를 최종 학적과 조인한다.

### 3.5 주소: `address_categories` + `address_rules`

규칙 종류(`kind`)는 세 가지만 둔다. 동·호수처럼 학생마다 달라지는 요소는 규칙에 넣지 않는다(§7).

| kind | pattern 예 | 매칭 방식 |
|---|---|---|
| `ROAD` | `한누리대로 123` | 정규화 주소에서 도로명+건물번호 토큰이 정확히 일치 |
| `COMPLEX` | `가온마을5단지` | 정규화 주소에 단지명이 포함 |
| `CONTAINS` | `○○빌라` | 단순 포함 (마지막 수단) |

판정 순서: **MANUAL 유지 → 사용자 규칙(ROAD → COMPLEX → CONTAINS) → 자동(`N단지` 패턴이 정확히 하나 발견되고 그 이름의 분류가 있을 때) → 확인 필요.** 두 규칙이 서로 다른 분류를 가리키면 자동으로 정하지 않고 ADDRESS issue에 두 후보를 적어 둔다.

### 3.6 `sibling_links`
`student_a < student_b`로 정규화한 쌍에 UNIQUE. `status`(CANDIDATE/CONFIRMED/REJECTED), `source`(AUTO/MANUAL), `matched_fields`·`conflict_fields`(JSON 배열). **REJECTED는 자동 탐색이 다시 후보로 올리지 않는다** — 사용자 판단을 자동화가 덮어쓰지 않기 위한 장치.

### 3.7 `issues`
`kind` ∈ ADDRESS · BIRTH · GUARDIAN_CONFLICT(보호자 불일치) · GUARDIAN_FILL(형제 정보로 보완 제안) · SIBLING_CANDIDATE · DUPLICATE · MISSING(학생 정보 누락) · CLASS_ASSIGN(반·번호 미정) · NUMBER_DUP(같은 반 번호 중복) · OTHER.
`message`(사용자 문장), `detail`(JSON 근거), `ref_id`(형제 연결 id 등), `status`(OPEN/RESOLVED/DISMISSED). 같은 학생·같은 종류·같은 참조의 열린 issue는 하나만 있도록 부분 UNIQUE 인덱스를 둔다.

**표시를 만드는 곳은 `repo::student::sync_issues` 한 곳뿐이다.** 학생을 저장할 때도,
가져오기 뒤에도, 주소를 다시 적용할 때도, 설정의 [확인 필요 다시 계산]도 모두 이 함수를
부른다. 그래서 어느 길로 들어와도 판정이 같고, 몇 번을 다시 돌려도 같은 문제가 두 줄로
쌓이지 않는다. **[해결] 버튼은 두지 않는다** — 원인이 사라져야 표시가 닫힌다.

'번호 중복' 처럼 **둘 이상이 함께 겪는 문제**는 고친 학생만 다시 따지면 상대 쪽 표시가
남는다. 그래서 `sync_number_peers` 로 떠나온 번호와 새로 앉은 번호의 이웃까지 함께 맞춘다.
형제 쪽은 `sync_issues_with_siblings` 가 같은 일을 한다.

### 3.8 마이그레이션
보결 배정 시스템과 같은 방식: `PRAGMA user_version` + `migrations/00N_*.sql` 번호순 적용, 적용 전 자동 백업(`before_migration_…`, SQLite 백업 API), 기존 파일은 절대 수정하지 않는다. **v0.1.0 릴리스로 `001_init.sql` 은 동결한다** — 이후 변경은 `002_*.sql` 부터 새 번호로만 한다(§5.12).

### 3.9 `renumber_ops` — 번호 재정렬 기록 (Phase 5)
번호 이동 한 번에 반 학생 열몇 명의 번호가 함께 바뀐다. 나중에 "내 번호가 왜 바뀌었지?"
를 되짚을 수 있도록 **작업 단위로 한 줄만** 남긴다. `school_year`, `grade`, `class_name`,
`student_id`(사용자가 고른 학생), `from_no`, `to_no`, `kind`, `moved`(바뀐 인원),
`plan`(JSON).

학생마다 `enrollment_events` 에 남기지 **않는** 이유: 그 표는 전입·전출·진급 같은 *학적
이동* 이력이다. 한 번 정렬할 때마다 사건이 열몇 개씩 쌓이면 정작 봐야 할 이동 기록이
묻힌다. 번호는 학적 이동이 아니라 반 안의 자리 정리다.

## 4. 화면 · 메뉴 구조

좌측 고정 사이드바(아이콘 + 메뉴명) + 우측 작업영역. 상단 바에 화면명 · 학년도 선택 · 주요 버튼.


## 5. 핵심 로직 설계

### 5.1 생년월일 정규화 (`domain::birth`)
숫자만 뽑아 6자리(`YYMMDD`) 또는 8자리(`YYYYMMDD`)면 변환한다. 6자리는 **올해 두 자리 이하 → 20YY, 아니면 19YY**. 변환 뒤 (a) 실제 존재하는 날짜인지, (b) 나이가 만 4~15세 범위인지 확인해 벗어나면 BIRTH issue를 연다. 자동 수정은 하지 않는다. 표시 형식은 `17.03.15.`.

### 5.2 연락처 정규화 (`domain::phone`)
숫자만 남긴다. 10~11자리 휴대전화(`01X`)는 `010-1234-5678`로, 그 외 길이는 원문을 유지하고 digits만 저장한다. 검색은 digits `LIKE`.

### 5.3 주소 정규화·분류 (`domain::address` + `repo::address`)

**원본은 절대 건드리지 않는다.** `address_raw` 는 사용자가 적은 그대로 두고, 그 곁에
정리값과 판정 결과를 따로 둔다.

| 열 | 내용 |
|---|---|
| `address_raw` | 입력 원문. 어떤 경우에도 고치지 않는다 |
| `address_norm` | 전각→반각, 이어진 공백 정리. 검색과 규칙 맞춤에 쓴다 |
| `address_road` | 뽑아낸 `도로명 건물번호`. **동·호수는 뺀다** |
| `address_category_id` | 정해진 분류 |
| `address_source` | 어떻게 정했는지 — NONE / AUTO / RULE / MANUAL / CONFLICT |
| `address_rule_id` | RULE 이면 어느 규칙이 정했는지 |

**`도로명 건물번호` 를 규칙의 기준으로 삼는 이유.** 같은 아파트라도
`○○로 123, 101동 1001호` `○○로 123 105동 804호` 처럼 동·호수가 제각각이다.
건물을 가리키는 부분만 뽑으면 이들이 하나의 규칙으로 묶인다. 로와 길이 겹치는
`○○로3길 25` 는 **더 좁은 길**을 쓰고, `○○로 123번길 45` 처럼 떨어져 있으면 앞 도로명을 붙인다.

**판정 순서**

1. `MANUAL` — 사용자가 이 학생만 직접 지정했다. 자동 재적용이 **절대** 건드리지 않는다
2. ROAD 규칙 — 도로명+건물번호가 **정확히** 같을 때만 (`○○로 12` 는 `○○로 123` 에 걸리지 않는다)
3. COMPLEX 규칙 — 단지 이름 포함 (띄어쓰기 무시)
4. CONTAINS 규칙 — 단순 포함. 넓게 걸리므로 맨 마지막
5. 주소에 적힌 단지 이름으로 자동 — `단지` 라는 말이 있고, 그 이름의 분류가 있을 때만
6. 그 밖에는 **미분류**

**정하지 않는 경우.** 같은 순위의 규칙 둘이 서로 다른 분류를 가리키면 고르지 않고
`CONFLICT` 로 둔다. 한 주소에 서로 다른 단지가 둘 이상 적혀 있어도 자동으로 정하지 않는다.
없는 분류를 만들어 내지 않고, **미분류를 '기타' 로 밀어 넣지도 않는다** —
'기타' 는 사람이 기타라고 정한 분류이고 '미분류' 는 아직 정하지 못한 상태다.

**확인 필요와의 연결.** 주소가 있는데 분류하지 못했거나 규칙이 부딪히면 `sync_issues` 가
ADDRESS 표시를 연다. 분류가 정해지면(직접 지정 포함) 저절로 닫힌다. 판정 규칙은
`sync_issues` 한 곳에만 있으므로 가져오기·재적용·손수정이 모두 같은 결과를 낸다.

**규칙을 만든 뒤.** 저절로 적용하지 않는다. 몇 명에게 걸리는지 세어 보여 준 뒤
사용자가 [N명에게 적용] 을 고른다. 직접 지정한 학생은 그 수에서 빠진다.

**주소를 고쳤을 때.** 예전 판정이 새 주소에도 맞다고 볼 수 없으므로 다시 따진다.
직접 지정한 분류가 있으면 화면이 **유지할지 다시 판정할지 묻는다**
(`StudentInput::keep_manual_address`). 조용히 예전 분류를 남기지 않는다.

### 5.4 형제 후보 (`domain::sibling` + `repo::sibling`)

**판정 규칙 (Phase 4 구현).** 비교 항목은 4개뿐이다 — 부 성명·모 성명·부 연락처·모 연락처.
**같은 항목끼리만** 견준다. A의 부 연락처와 B의 모 연락처처럼 엇갈려 견주지 않는다.

| 상황 | 판정 |
|---|---|
| 양쪽 다 값이 있고 같다 | 일치 (`matched_fields`) |
| 양쪽 다 값이 있는데 다르다 | 불일치 (`conflict_fields`) |
| 한쪽이라도 빈칸이다 | 일치도 불일치도 아니다 |

**빈칸끼리는 절대 일치가 아니다.** 빈칸 두 개를 일치로 세면 보호자 정보가 없는 학생끼리
모두 형제가 된다. 값이 있는 항목이 **2개 이상**(`MIN_MATCHES`) 같아야 후보다.

정규화는 Phase 1 것을 그대로 쓴다 — 연락처는 `phone::digits`, 이름은 공백만 없앤다.
`김 영희`와 `김영희`는 같은 사람이지만 `김영희`와 `김영이`는 다른 사람이므로
비슷한 이름을 묶지 않는다. 연락처는 `phone::is_comparable`(9자리 이상)을 통과한 값만
일치로 센다 — 네 자리쯤 되는 값은 우연히 겹친다.

**성능.** 1,000명을 전수 비교하면 50만 쌍이다. 대신 네 항목의 값으로 해시맵 버킷을
만들어 **같은 값을 가진 학생끼리만** 견준다(`find_pairs`). 같은 값을 `BUCKET_LIMIT`(30)명
넘게 나눠 가진 항목은 사람을 가려내지 못하므로 후보를 만드는 데 쓰지 않고 몇 건인지만
알린다(`skipped_values`) — 학교 대표번호를 모든 학생에게 적어 둔 자료가 그런 경우다.
대상은 **그 학년도 재학생(재학+전입, 졸업 제외)** 만.

**사용자의 판단은 지운다고 되살아나지 않는다.** 다시 훑을 때 기존 링크는 근거
(`matched_fields`·`conflict_fields`)만 갱신하고 `status`는 건드리지 않는다. 근거가
사라진 `CANDIDATE`만 지우고, `CONFIRMED`와 `REJECTED`는 남긴다. **거부한 관계를
다시 후보로 올리지 않는다.**

**확정 뒤 보완 제안.** 한쪽만 비어 있는 보호자 항목이 있으면 GUARDIAN_FILL issue,
양쪽 다 있는데 다르면 GUARDIAN_CONFLICT issue. 채우기는 **항상 사용자가 고른 항목만**
`UPDATE ... WHERE (col IS NULL OR TRIM(col) = '')` 로 넣으므로 있는 값을 덮어쓰지 않는다.
불일치는 프로그램이 고르지 않고, **불일치가 있다고 형제 관계를 취소하지도 않는다.**

**표시 문자열은 저장하지 않는다.** `sibling_links`에는 학생 번호만 두고 `1-나리 홍길동`
같은 이름표는 볼 때마다 지금 학적으로 만든다. 그래서 형제가 진급해도 표시가 저절로 최신이다.

**가져오기와의 관계.** 1,200줄을 넣을 때 줄마다 전체 재탐색을 돌리면 같은 일을 1,200번
한다. `import::apply`는 학생을 모두 저장한 **뒤에 한 번만** `sibling::scan`을 부르고,
관계가 걸린 학생의 표시만 다시 맞춘다.

### 5.5 번호 재정렬 (`domain::renumber` + `repo::renumber`)

입력은 같은 학년도·학년·반 학생 전부(`Seat { student_id, class_no }`), 대상 학생, 새 번호.
출력은 `Plan { kind, moves: [Move { student_id, from, to }] }` 로, **실제로 번호가 달라지는
학생만** 담는다.

**계산 방법: 번호 집합은 그대로 두고 줄만 바꾼다.** 번호순으로 줄을 세운 뒤 대상 학생을
빼고 새 번호의 자리에 다시 끼워 넣은 다음, **원래 있던 번호들을** 차례대로 나눠 준다.
한 규칙으로 두 방향이 모두 나온다 — 23→7 이면 7~22 가 한 칸씩 밀리고, 7→23 이면
8~23 이 한 칸씩 당겨진다.

이 방법을 쓰는 까닭은 **띄엄띄엄한 번호를 망가뜨리지 않기 위해서**다. `1,2,3,5,6,9` 인
반에서 9번을 3번으로 옮기면 `1,2,3,5,6,9` 가 그대로 유지된 채 주인만 바뀐다. 없던
4·7·8번이 생기지 않고, 반 전체를 1~N 으로 다시 매기지도 않는다.

| 상황 | `kind` | 결과 |
|---|---|---|
| 이미 그 번호다 | `NONE` | 아무것도 하지 않는다 |
| 새 번호가 **비어 있다** | `ASSIGN` | 그 학생만 바뀐다. 다른 학생은 건드리지 않는다 |
| 새 번호를 남이 쓰고 있다 | `REORDER` | 사이 학생들이 한 칸씩 밀린다 |
| 번호가 **없던** 학생을 남의 번호에 넣는다 | `INSERT` | 뒤가 한 칸씩 밀리고 반의 번호가 하나 늘어난다 |

막는 경우: 번호가 1~200 밖일 때, 그 반에 그 학생이 없을 때, **그 반에 이미 겹치는 번호가
있을 때**(누구를 밀어야 할지 정할 수 없다). 다만 겹친 학생을 **빈 번호로 비켜 세우는 것은
막지 않는다** — 그것이 중복을 푸는 방법인데 막으면 빠져나갈 길이 없어진다.

**미리보기와 적용을 나눈다**(Phase 2 가져오기와 같은 원칙). `preview` 는 DB 를 건드리지
않고 계획과 `state_key`(그 반의 번호 상태를 줄인 값)를 돌려준다. `apply` 는 저장 직전에
**같은 자료로 다시 계산**하고, `state_key` 가 달라졌으면 `STALE` 오류로 거절한다. 오래된
미리보기로 엉뚱한 학생의 번호를 바꾸는 일을 막는다. 저장은 `Db::write` 트랜잭션 하나
안에서 끝나므로 중간에 실패하면 한 명도 바뀌지 않는다.

적용 뒤에는 **그 반 학생 전부**의 확인 필요를 다시 따진다. 번호가 그대로인 학생도 짝이
비켜 주면 '번호 중복' 이 풀리기 때문이다. 주소나 형제까지 다시 훑지는 않는다.

기록은 `renumber_ops` 에 **작업 한 줄**만 남긴다(§3.9). 앞으로 "가나다순 1~N 다시 매기기"
같은 기능을 더할 때도 `Plan` 을 만드는 함수만 늘리면 되고, 저장·미리보기·기록은 그대로 쓴다.

### 5.6 가져오기 파이프라인 (`import`)

**읽기 → 짝짓기 → 분석 → (사람이 확인) → 적용**. 분석까지는 DB를 건드리지 않는다.

| 모듈 | 하는 일 |
|---|---|
| `excel` | 시트 목록·크기, 시트를 글자표로 읽기. 숫자 칸(`170315.0`)과 날짜 칸을 글자로 옮기고, 앞자리 0이 빠진 연락처(`1012345678`)를 되살린다 |
| `mapping` | 별칭표로 열을 추측(이름/성명/학생명, 반/학급, …). 한 열이 두 항목에 겹치지 않게 점수 높은 짝부터 확정한다. 제목 줄이 있는 파일을 위해 헤더 줄도 찾는다 |
| `row` | 한 줄에서 값 꺼내기. 학년(`3학년`→3)·성별(남/M/1)을 알아보고, 생년월일은 `domain::birth` 에 맡긴다. 이름·학년이 없는 줄만 '가져올 수 없음'으로 막는다 |
| `analyze` | 기존 학생과 견주어 추가/갱신/변경 없음/중복 의심 판정 + 항목별 이전→이후 |
| `apply` | 한 트랜잭션으로 저장. `repo::student::create`/`update` 와 `sync_issues` 를 그대로 쓴다 |

**같은 학생인지 가리는 순서** (§11.2 의 보수적 원칙)

1. **이름 + 생년월일**이 딱 하나 걸리면 같은 학생
2. 생년월일이 없으면 **그 학년도의 같은 자리(학년·반·번호) + 같은 이름**으로 가린다
3. 생년월일은 있는데 걸리는 학생이 없고 같은 자리에 같은 이름이 있으면 → **중복 의심**
   (생년월일이 고쳐진 것인지 다른 학생인지 알 수 없다)
4. 이름만 같으면 동명이인일 수 있다 → 생년월일이 다르면 **신규**, 생년월일이 없으면 **중복 의심**
5. 한 파일 안에서 같은 학생을 두 줄이 가리키면 뒤엣것을 **중복 의심**

**중복 의심과 가져올 수 없음은 저장하지 않는다.** 목록에 남겨 사람이 처리한다.

**엑셀 빈칸은 기존 값을 지우지 않는다** (`analyze::merge`). 값이 있을 때만 바꾼다.
'빈칸도 반영' 옵션이 필요해지면 그 함수에 갈래를 하나 더한다.

적용은 분석을 **트랜잭션 안에서 다시 돌린 뒤** 저장한다. 미리보기와 실제 결과가 어긋날
여지를 없애기 위해서다. 분석 결과는 화면이 아니라 Rust 쪽(`import::SessionStore`)에 두어,
되돌아온 값을 그대로 믿지 않고 두 번 누르는 것도 막는다.

진행 상황은 `ANALYZE`(자료 분석) → `SAVE`(학생정보 저장) → `FINISH`(마무리) 세 단계로
`job://progress` 에 실어 보낸다(§7.2). 줄마다 보내지 않고 전체의 1%마다 보낸다.

### 5.7 학년도 전환 (`domain::transition` + `transition` + `repo::transition`)
**지난 학년도를 고치지 않는다.** 2026학년도 3-가람-7 은 그대로 두고 2027학년도 4-나리-12 를
**새로 만든다**(`INSERT`). 학생 번호(`students.id`)가 그대로이므로 형제 관계·지난 이력이
모두 이어진다. 이 모듈에 `UPDATE enrollments` 는 한 줄도 없다.

```
원본 학년도 재학생 ──┐
                     ├─▶ build() ─▶ 계획 확인 ─▶ 백업 ─▶ 한 트랜잭션(apply)
진급 배정 파일 ──────┘
```

1. 대상 = 원본 학년도 **현재 재학생**(`ACTIVE_STATUS_SQL`, §5.9). 지금 전출 상태면 빠진다
2. 배정 파일과 짝짓기: **학생번호 → (기존 학년·반·번호) → 이름+생년월일**. 파일은 사람이
   고칠 수 있으므로 학생번호도 DB 와 견주고, 이름이 다르면 다른 학생일 수 있다고 막는다
3. 새 학년은 파일 값(없으면 +1). 6학년은 `graduations` 행 + `GRADUATE` 사건
4. 번호는 **전부 있거나 전부 없어야 한다.** 전부 없으면 이름 가나다순 1~N(명단 정렬과 같은
   규칙), 일부만 있으면 **채우지 않고 막는다** — 사람이 의도한 자리가 깨지기 때문이다
5. 진급은 `PROMOTE` 사건(`source = TRANSITION`)을 남기고, 작업 자체는 `year_transitions`
   한 줄(학년도와 인원만, 개인정보 없음)
6. 적용 직전 **자동 백업**(`before_year_transition_2026_to_2027_YYYYMMDD_HHMMSS.db`).
   백업이 실패하면 트랜잭션을 열지 않는다
7. 미리보기 이후 명단이 바뀌었으면 `state_key`(FNV, §5.5 와 같은 방법)가 달라져 `STALE` 로
   거절한다. 적용은 **트랜잭션 안에서 계획을 다시 세워** 미리보기와 어긋날 수 없게 한다

**막는 것과 알리는 것을 나눈다.** 새 반이 없거나 번호가 겹치면 학적을 만들 수 없으니 막고,
기존 자리가 파일과 다르거나 기본 진급과 다른 학년이면 알리기만 한다 — "오류가 있어도 입력을
막지 않는다" 는 원칙은 그대로 두되 **만들 수 없는 것만** 막는다.

진급 배정 양식은 Phase 8 내보내기 엔진의 프리셋(`Preset::Promotion`)이다. 열 정의
(`domain::transition::Col`)를 양식을 만들 때도 읽을 때도 함께 쓰므로 어긋나지 않는다.
개인정보는 최소로 — 학년·반·번호·이름·생년월일뿐이고 보호자·주소는 넣지 않는다.

**신입생은 전환 트랜잭션 밖이다.** 전환이 끝난 뒤 기존 가져오기 화면(`?year=2027&grade=1`)으로
넣는다. Phase 2 엔진을 그대로 지나므로 정규화·주소 판정·중복 탐색·형제 후보·확인 필요가
모두 같은 규칙으로 이루어지고, 가져오기 자체가 한 트랜잭션이라 반쯤 들어가는 일도 없다.

### 5.8 졸업생 (`repo::graduation`)
졸업생을 **따로 복사해 두지 않는다.** 학생 자료는 한 벌이고 졸업은 그 학생에게 붙는 기록이다.
졸업 당시 학년·반·번호는 그 학년도 학적이 그대로 갖고 있다(전환이 지난 학년도를 고치지
않으므로 흐트러지지 않는다). 졸업하면 다음 학년도 학적이 없으므로 현재 명단·통계·본교 형제
계산에서 저절로 빠지고, 형제 관계 기록은 남되 이름표에 `졸업` 이 붙는다.

졸업 취소는 **사건을 지우지 않는다.** 졸업 기록만 없애고 `CANCEL` 을 덧붙인다(전출 취소와
같은 방법). 되돌린 학생은 그 학년도 명단으로 돌아오고, 다음 학년도 학적은 사람이 정한다.

### 5.9 전입 · 전출 (`domain::enroll` + `repo::transfer`)

**학생을 새로 복제하거나 지우는 기능이 아니다.** 사람은 하나로 두고 학적의 상태만
바꾸며, 언제 무슨 일이 있었는지를 `enrollment_events` 에 덧붙인다.

**현재 재학생이 무엇인지 한 곳에서 정한다.** `domain::enroll::ACTIVE_STATUS_SQL` 이
그 정의이고, 학생명단·주소 재적용·형제 탐색·번호 재정렬·반별 인원·학년도 인원·확인
필요 업무함이 모두 이 한 줄을 쓴다. 전입생은 **들고**, 전출생은 **빠진다**.

| 경우 | 학적 | 사건 |
|---|---|---|
| 처음 오는 학생 | 그 학년도 학적을 새로 만든다 | `TRANSFER_IN` (등록 사건은 남기지 않는다) |
| **같은 학년도**에 나갔다 돌아옴 | 있던 학적을 **되살린다**. 행을 더 만들지 않는다 | `TRANSFER_OUT` 다음에 `TRANSFER_IN` |
| 다른 학년도 재전입 | 그 해 학적만 새로 만든다. 지난 학적은 손대지 않는다 | `TRANSFER_IN` |
| 전출 | 상태만 `TRANSFER_OUT`. 지우지 않는다 | `TRANSFER_OUT` (그때의 학년·반·번호 스냅샷) |
| 전출 취소 | 나가기 전 상태로 되돌린다 | `CANCEL` — **전출 사건은 지우지 않는다** |
| 지난 전출생 직접 넣기 | 처음부터 `TRANSFER_OUT` 으로 만든다 | `TRANSFER_OUT` |

전출을 취소할 때 사건을 지우지 않는 까닭: 지워 버리면 잘못 눌렀다는 사실조차 사라져
나중에 무엇이 맞는지 알 수 없다. 상태만 되돌리고 되돌린 기록을 함께 남긴다.

**기존 학생 찾기.** 이름·생년월일로 후보를 찾아 **지난 학적과 함께** 보여 준다.
이름이 같다는 것만으로 같은 학생이라고 정하지 않는다 — 고르는 것은 사람이다.
Phase 2 가져오기의 원칙과 같다.

**이동 날짜는 이 작업의 본체다.** 빠진 값이 있어도 저장을 막지 않는 것이 이 프로그램의
원칙이지만, 날짜가 틀리면 남는 이력 자체가 거짓이 된다. 그래서 세 가지는 막는다 —
아직 오지 않은 날, 그 학년도(3월 1일~다음 해 2월 말일) 밖의 날, **앞선 이동보다 이른 날**.

**같은 이동을 두 번 적지 않는다.** 마지막 사건과 종류·날짜가 같으면 새로 적지 않는다.
버튼을 두 번 눌러도 안전하고, 취소한 뒤 같은 날로 다시 처리하는 경우는 마지막 사건이
`CANCEL` 이므로 정상적으로 적힌다.

**반 배정은 프로그램이 하지 않는다.** 학년을 고르면 반별 남/여/미입력 인원과 고른 반의
전입 후 예상만 보여 준다. 학생 수가 가장 적은 반을 권하지도, 강조하지도 않는다 —
실제 학교에는 인원 말고도 따질 것이 많다.

**성별이 비어 있는 학생을 남·여 어느 쪽에도 넣지 않는다**(`repo::stats`). 따로 세어
보여 준다. 남 + 여 가 합계와 다른데 까닭을 알 수 없는 표를 만들지 않기 위해서다.
이 집계는 화면 전용이 아니라 Phase 7 통계가 그대로 쓴다.

**곁가지 연결.** 전입 즉시 주소 규칙이 적용되고(Phase 3) 확인 필요가 만들어지며,
번호가 겹치면 저장은 되고 `NUMBER_DUP` 표시가 켜진다(Phase 5). 형제는 **그 학생에
걸린 쌍만** 찾는다(`sibling::scan_for_student`) — 한 명이 들어왔다고 학교 전체를 다시
훑지 않는다. 전출하면 관계는 남되 '본교 형제' 수에서는 빠지고 화면에 `전출` 이라고 적힌다.

**전출한 학생의 확인 필요는 업무함에서 빠진다.** 자료를 지우지는 않으므로 전출을
되돌리면 함께 돌아온다. 오늘 할 일을 가리지 않으면서 기록은 지키는 방법이다.

### 5.10 통계 (`repo::stats`)

**학생명단에 보이는 인원과 통계 숫자가 다르면 둘 다 못 쓴다.** 그래서 세는 기준을
따로 만들지 않는다. 모집단은 `StatFilter` 하나이고, 그 안에서 재학생 조건은
`domain::enroll::ACTIVE_STATUS_SQL`(§5.9)을 쓴다. 명단·전입 반 배정·통계가 같은 뜻이다.

**한 화면의 표는 한 번에 센다.** `stats_overview` 명령 하나가 전체·학년별·학년×반별·
주소 교차표·주소 품질을 같은 순간의 자료로 만든다. 표마다 따로 물으면 그 사이에 자료가
바뀌어 한 화면 안에서 숫자가 어긋날 수 있다.

| 표 | 무엇을 세나 |
|---|---|
| 전체 | 남 · 여 · 성별 미입력 · 합계 |
| 학년별 | **학생이 있는 학년만**. 1~6을 미리 박아 두지 않는다 |
| 학년 · 반별 | 반이 정해지지 않은 학생은 `미정` 으로 센다 (빠뜨리면 반 합계가 전체와 달라진다) |
| 주소 분류 × 학년 | 분류마다 한 줄, 그리고 `미분류` 와 `주소 없음` 을 따로 한 줄씩 |

**성별이 비어 있는 학생을 남·여 어느 쪽에도 넣지 않는다.** 따로 센다. 어느 표에서나
남 + 여 + 미입력 = 합계가 성립해야 한다.

**주소는 세 상태를 절대 섞지 않는다.**

| 상태 | 뜻 |
|---|---|
| 분류(`기타` 포함) | 사람이 정했거나 규칙으로 정해졌다 |
| `미분류` | 주소는 있는데 아직 정하지 못했다 — 밀린 일이다 |
| `주소 없음` | 주소 자체가 없다 |

'기타' 는 사람이 정한 분류이고 '미분류' 는 아직 아무도 정하지 못한 상태다. 합치면
정리된 자료와 해야 할 일이 섞여 어느 쪽도 보이지 않는다.

**스스로 견준다**(`check_consistency`). 전체 · 성별 합 · 학년 합 · 반 합 · 주소 합 ·
교차표 모든 칸의 합이 서로 같은지 볼 때마다 확인하고, 어긋나면 화면이 그 사실을 알린다.
검사에서도 이 함수 하나로 모든 표를 한꺼번에 본다.

**집계를 저장하지 않는다.** Phase 3 에서 규칙의 적용 학생 수를 세어 두지 않은 것과 같은
까닭이다 — 세어 둔 값은 언젠가 실제 자료와 어긋난다. 2,000명에서 모든 표를 한 번 세는 데
13ms 였으므로(debug 빌드) 캐시를 둘 까닭이 없다.

**지난 학년도는 그 해 학적으로 센다.** `enrollments` 가 학년도마다 한 줄이고 학년·반·번호를
그 시점 값으로 들고 있으므로, 지금 3-나리인 학생도 2025학년도 표에서는 2-가람으로 나온다.
그 학년도의 `status` 는 **그 해 마지막 상태**이므로 지난 학년도 통계는 *학년도 최종 재적*
기준이다 — 그 해 중간에 전출한 학생은 빠진다. 화면 오른쪽 위에 어느 기준인지 적어 둔다.

**조건은 앞으로도 같은 것을 쓴다.** `StatFilter`(학년도 · 학년 · 주소 상태)는 학생명단의
`ListFilter` 와 같은 뜻으로 맞춰 두었다. 통계에서 숫자를 누르면 그 조건 그대로 명단이
열리고 인원이 정확히 같다. Phase 8 내보내기도 이 조건을 그대로 받는다.

**반 정렬은 한 곳에서 정한다**(`label::ORDER_BY_CLASS`). 명단과 통계가 반을 다른 차례로
늘어놓으면 같은 자료가 다른 표처럼 읽힌다.

### 5.11 출력 모듈 (`domain::export` + `export` + `repo::export`)
사용자 지정 Excel · 학교종이 · 알림e 를 **서로 다른 출력 코드로 만들지 않는다.** 셋은
같은 길을 지난다.

```
ListFilter ──▶ repo::export::rows ──▶ preset::{custom|schooljongi|alime} ──▶ ExportPlan ──▶ export::write_plan
  (누구를)         (명단과 같은 차례)        (어떤 열 · 어떤 파일로)            (미리보기 = 결과)      (.xlsx)
```

**열 정의의 원본은 `domain::export::Column` 하나다.** 키·표시명·Excel 머리글·개인정보
여부·너비를 한 곳에 두고, 화면은 `export_columns` 로 받아 그린다. 화면이 열 이름을
따로 적어 두면 모델이 바뀔 때 조용히 어긋난다.

**필터와 묶기는 다른 개념이다.** `ListFilter` 는 *누구를* 뽑을지, `Grouping`
(`ALL`/`GRADE`/`GRADE_CLASS`)은 *몇 개 파일로* 나눌지를 정한다. 그래서 "3학년만 뽑아
반별로", "5단지만 뽑아 학년별로" 가 따로 만든 코드 없이 나온다. 알림e 의 1,000명 제한은
**필터 → 묶기 → 묶음별 1,000명 자르기** 차례로 건다. 전체를 먼저 자르면 한 파일에 여러
학년이 섞여 쓸 수 없는 명단이 된다.

지키는 것

* **모든 칸을 글자로 쓴다.** `.xlsx` 의 글자 칸은 Excel 이 수식으로 계산하지 않고
  (`=`·`@` 로 시작하는 값이 그대로 남는다), `01012345678` 앞의 0 도 사라지지 않는다.
* **학생 자료를 고쳐 내보내지 않는다.** 주소는 원본(`address_raw`), 주소 분류는 별도 열.
  날짜로 읽지 못한 생년월일은 원본 그대로 내보낸다. 이름은 규격을 넘어도 자르지 않는다.
  규격에 맞추려 줄이는 것은 시스템이 만든 값(알림e 비고)뿐이다.
* **조용히 빼지 않는다.** 반이 없어 학급 시트를 만들 수 없는 학생, 전화번호가 없는 학생,
  15자를 넘는 값은 만들기 전에 이름표와 함께 알리고, 눌러서 기존 학생 창에서 고칠 수 있다.
* **저장 위치는 사용자가 고른다.** 파일이 하나면 저장 창, 여럿이면 폴더 창. 같은 이름이
  있으면 덮어쓸지 먼저 묻는다. 창을 닫은 것(취소)은 오류가 아니다.

프리셋이 늘어도 `preset.rs` 에 함수 하나가 늘 뿐, 파일 쓰기·이름 짓기·미리보기는 그대로다.

### 5.12 운영 — 백업 · 복원 · 자료 구조 · 업데이트 (`db::backup`, `commands::backup`)

학생 자료는 이 컴퓨터 안에만 있다. 그래서 **되돌릴 수 있는 것**이 마지막 안전장치다.

**파일을 복사하지 않는다.** DB 는 WAL 모드라 `.db` 만 베끼면 아직 반영되지 않은 내용이
빠진다. 모든 백업은 SQLite 백업 API(`Db::backup_to`)로 한 시점을 통째로 뜨고, 백업본은
`journal_mode=DELETE` 로 바꿔 **한 파일**로 만든다(USB 로 하나만 옮겨도 온전하다).

**만들었다고 성공이 아니다.** 만든 파일을 다시 열어 `integrity_check`, 이 프로그램의 표가
있는지, 자료 구조 버전이 읽을 수 있는 범위인지 확인한다. 실패한 파일은 지우고 알린다 —
믿을 수 없는 백업을 정상으로 표시하면 정작 되돌릴 때 더 나쁘다.

| 종류 | 언제 | 자동 정리 |
|---|---|---|
| `auto_…` | 앱을 연 날마다 한 번 (그날 것이 있으면 건너뛴다) | ○ 최근 30개 |
| `manual_…` | [지금 백업] | ✕ |
| `before_year_transition_…` | 학년도 전환 직전 (§5.7) | ✕ |
| `before_restore_…` | 복원 직전 | ✕ |
| `before_migration_…` | 자료 구조를 올리기 직전 | ✕ |

자동 백업은 **자료가 성할 때만** 만든다. 앱을 열 때 `integrity_check` 를 한 번 보고,
문제가 있으면 백업을 만들지 않고 화면 위에 빨간 줄로 알린다 — 손상된 자료로 뜬 백업이
멀쩡한 지난 백업을 밀어내면 되돌릴 곳이 사라진다.

**복원은 열려 있는 파일을 바꿔치기하지 않는다.**

```
고른 파일 확인 → studentroster.db.restore-pending 로 놓아 둠 → 사용자가 앱 종료
   → 다음 실행: 연결을 열기 전에  ① 다시 확인  ② 지금 자료를 before_restore_ 로 백업
                                  ③ WAL 치우고 rename 으로 갈아 끼움
```

어느 단계에서 멈춰도 지금 자료가 남는다. 놓아 둔 파일이 그사이 망가졌으면 갈아 끼우지
않고 옆으로 치운 뒤 기존 자료를 그대로 연다. 자동 재시작을 쓰지 않는 까닭은 자료 파일을
바꾸는 도중에 두 프로세스가 같은 파일을 보는 일을 막기 위해서다.

**자료 구조는 v0.1.0 릴리스로 동결한다.** `001_init.sql` 은 더 이상 고치지 않는다.
바꿀 일이 생기면 `002_*.sql` 을 새로 더하고 `MIGRATIONS` 에 한 줄 추가한다. 러너는
`PRAGMA user_version` 보다 높은 번호만 차례로 적용하고, **적용 직전에 자동 백업**한다.
더 높은 버전의 자료는 `SCHEMA_TOO_NEW` 로 열지 않는다(복원에서도 같은 이유로 막는다).

**업데이터**는 GitHub 릴리스의 `latest.json` 을 본다. 하루 한 번 저절로 확인하고
(`settings.update_checked_at`), 사용자가 누를 때는 바로 확인한다. 확인 실패는 앱 사용을
막지 않는다 — 오프라인에서도 모든 기능이 그대로 돌아간다. 내려받은 파일은 minisign
서명을 확인한 뒤에만 설치한다. **`relaunch()` 는 부르지 않는다** — Windows 에서
`install()` 은 돌아오지 않고 앱을 스스로 끝내며 NSIS 가 다시 켠다. 여기서 relaunch 를
부르면 설치 프로그램과 경쟁해 업데이트가 조용히 실패한다(다른 앱에서 겪은 버그다).

로그에는 학생 이름·생년월일·주소·보호자·연락처를 남기지 않는다. 종류·인원·크기·버전만
남긴다. 이 앱은 로거를 설치하지 않으므로 실제로 파일에 쌓이는 로그도 없다.

## 7. 화면-백엔드 규약

### 7.1 명령(IPC)
`commands/<영역>.rs` 의 `#[tauri::command]` ↔ `src/ipc/<영역>.ts`. 오류는 항상 `AppError { code, userMessage, detail }`. 화면은 `userMessage`만 보여주고 `detail`은 [자세히] 접기.

### 7.2 진행률 이벤트
장시간 작업은 `job_id`를 반환하고 스레드에서 `emit("job://progress", {jobId, stage, stageLabel, done, total})` → 끝나면 `job://done {jobId, result}` 또는 `job://error`. 화면은 이벤트를 구독해 진행률 UI를 그린다. 가져오기·학년도 전환·형제 재탐색·주소 재적용이 이 규약을 쓴다.

### 7.3 명명
DB·Rust는 snake_case, IPC JSON은 camelCase(`serde(rename_all)`), 날짜는 `YYYY-MM-DD` 문자열, 시각은 로컬 `YYYY-MM-DD HH:MM:SS`.

## 10. 확인이 필요한 요구사항 (임시 결정 포함)

1. **6자리 생년월일의 세기** — 임시: 올해 두 자리 이하면 20YY. 초등학생 범위(만 4~15세)를 벗어나면 확인 필요.
2. **주소 규칙 "도로명+건물번호" 토큰이 없는 주소**(지번 주소, 아파트명만 있는 경우) — 임시: COMPLEX/CONTAINS 규칙으로 처리, 없으면 확인 필요.
3. **반 순서** — 임시: 숫자 → 가나다. 학교가 정한 순서(가람·나리·다솜…)가 가나다와 다르면 설정에 학년별 반 순서 지정 기능을 Phase 7 전에 추가.
4. **학생명단의 기본 정렬** — 임시: 학년 → 반 → 번호 → 이름.
5. **필수값** — 임시: 학년도·학년·이름만 필수. 반·번호·성별은 비어 있어도 등록하고 MISSING issue.
6. **전출 후 재전입** — 임시: 같은 학년도면 학적 행을 되살린다(전출일은 비고로 이동). 다른 학년도면 새 학적 행.
7. **형제 판정에서 교차 비교**(A의 부 번호 = B의 모 번호) — 임시: 하지 않는다(요구사항 그대로 같은 항목끼리).
8. **6학년 중 유예·미졸업** — 결정: 전환 미리보기에서 학생별 졸업 대상 체크를 끄면 졸업도 진급도 하지 않는다(다음 학적 없음, 알림만). 6학년을 한 해 더 두려면 배정 자료에 그 학생의 새 학년 6 과 반을 적는다 — 프로그램이 7학년을 만들지 않는다.
9. **DB 암호화** — 임시: 하지 않는다. 사용자 계정 폴더 저장 + 안내. 필요하면 SQLCipher(rusqlite `bundled-sqlcipher`)로 교체 가능한 구조(DB 접근이 `Db` 한 곳).
10. **학교종이·알림e 양식** — Phase 8에서 확인한 열 구성으로 넣었다(학교종이: 번호·이름·보호자휴대폰1·보호자휴대폰2·학생휴대폰 / 알림e: 이름·전화번호·비고). 양식이 바뀌면 `export::preset` 의 함수 하나만 고친다.
11. **주보호자 연락처가 비었을 때** 부/모 연락처로 채울지 — 결정: 저장된 자료는 그대로 두고, **외부 양식(학교종이·알림e)에서만** 주보호자 → 모 → 부 차례로 채운다. 사용자 지정 Excel 은 고른 열의 값을 그대로 낸다.
12. **가져오기 시 기존 학생과의 관계** — 임시: 가져오기는 "해당 학년도에 추가"이며 기존 학생을 갱신하지 않는다. 같은 이름+생년월일이 있으면 DUPLICATE issue. (기존 명단 갱신 모드는 필요해지면 Phase 2 후반에 추가)

## 11. 설계 재검토 (Phase 1 착수 전, 2026-09-15)

§10 의 임시 결정을 사용자가 확인하면서, 두 항목은 **실제 학교 업무와 이력 보존 관점에서
다시 보라**는 요청이 있었습니다. 검토 결과 둘 다 문제가 있어 `001_init.sql` 을 고쳤습니다
(첫 배포 전이므로 새 마이그레이션 번호 없이 초기 스키마를 직접 수정).

### 11.1 전출 후 같은 학년도 재전입 — **설계 변경**

| | |
|---|---|
| **기존 설계** | `enrollments` 행 하나를 `TRANSFER_OUT` → `TRANSFER_IN` 으로 되돌리고, 이전 전출 정보는 `transfer_out_note` 에 글로 남긴다 |
| **문제** | `enrollments` 는 `UNIQUE(student_id, school_year)` 라 한 학년도에 한 행이다. 그런데 전출·전입은 한 해에 두 번 이상 일어날 수 있다. 두 번째 이동이 첫 번째를 **덮어쓰고**, 이력은 자유 글로만 남아 조회·집계·내보내기에 쓸 수 없다. 요구사항 §15 의 "전출일·기존 학년/반/번호 기록"도 두 번째 이동 뒤에는 첫 번째 값을 잃는다 |
| **변경** | `enrollment_events` 표를 새로 만든다. 이동을 **사건으로 덧붙이기만** 한다 (고치지도 지우지도 않는다). `kind`(ENROLL/TRANSFER_IN/TRANSFER_OUT/PROMOTE/GRADUATE/CANCEL), `event_date`, 그 시점의 `grade`·`class_name`·`class_no` 스냅샷, `note`, `source`(MANUAL/IMPORT/TRANSITION) |
| **이유** | 현재 상태(`enrollments`)와 이력(`enrollment_events`)은 쓰임이 다르다. 명단·통계는 "지금 어디 반인가"만 필요하므로 한 행이 빠르고 중복이 안 생긴다. 이력은 "언제 무슨 일이 있었나"라 여러 줄이어야 한다. 둘을 한 표에 욱여넣으면 둘 다 나빠진다 |
| **어긋남 방지** | `enrollments` 의 `transfer_in_date`·`transfer_out_date` 는 **가장 최근 값의 사본**으로 남겨 조회를 단순하게 하되, 쓰는 길을 `repo::student` 한 곳으로 묶어 사건과 현재 상태를 같은 트랜잭션에서 함께 바꾼다 |

Phase 1 은 등록 시 `ENROLL` 사건만 남긴다. 전입·전출(Phase 6)과 진급·졸업(Phase 9)이
같은 자리에 줄을 더하면 되고, **그때 스키마를 고칠 일이 없다.**

### 11.2 기존 학생이 있는 상태에서 Excel 다시 가져오기 — **설계 보강**

| | |
|---|---|
| **기존 설계** | 가져오기는 "추가"만 하고, 이름+생년월일이 같으면 중복 issue 를 연다 |
| **문제** | 실제로는 ① 최초 전체 명단 ② 고친 명단 다시 넣기 ③ 학기 중 새 자료 반영 이 모두 일어난다. "추가만" 하면 ②③ 에서 학생이 두 벌로 쌓인다. 그리고 갱신을 하려면 **쓰기 전에 무엇이 바뀌는지 보여 줘야** 하는데, 읽으면서 바로 저장하는 구조로는 미리보기를 만들 수 없다 |
| **변경** | (가) 가져오기를 **분석(미리보기) → 적용** 두 단계로 못박는다. 분석 단계는 아무것도 쓰지 않고 행마다 `추가 / 갱신 / 중복 의심 / 건너뜀` 과 항목별 `이전 → 이후` 를 만든다. (나) `imports` 표에 `mode`(ADD/UPDATE/BOTH), `added`·`updated`·`skipped`, `sheet_name`, `mapping`(열 짝짓기 JSON)을 둔다 |
| **이유** | 두 단계로 나누는 것은 **구조**라서 나중에 바꾸기 어렵다. 반면 갱신 화면 자체는 Phase 2 에서 만들면 된다. 지금은 막히지 않게만 해 둔다. `mapping` 을 남겨 두면 다음 가져오기에서 열 짝짓기를 다시 하지 않아도 된다(§9 위험 대응) |
| **덮어쓰기 방지** | 항목마다 "누가 고쳤는지"를 따로 저장하지 않는다. 대신 갱신 미리보기에서 **항목별 이전 → 이후를 보여 주고 사용자가 고른다.** 주소 분류만은 예외로 `address_source = MANUAL` 을 두어 자동 재분류가 건드리지 않는다 (요구사항 §24-6) |

### 11.3 그 밖에 바꾼 것

| 항목 | 내용 |
|---|---|
| `issues.kind` 에 `NUMBER_DUP` 추가 | 같은 반에 같은 번호가 둘 이상인 상태. **번호에 UNIQUE 제약을 걸지 않기로** 했기 때문에 필요하다 — 제약을 걸면 (가) 학기 초 정리 중 잠깐 겹치는 것이 막히고 (나) 번호가 겹친 엑셀 파일을 못 받아 "오류가 있어도 입력을 막지 않는다"(§24-1)가 깨진다. 막는 대신 표시한다 |
| `issues.kind` 갈래 정리 | `MISSING` 은 학생 정보(성별·생년월일·주소·연락처), `CLASS_ASSIGN` 은 학적(반·번호)으로 나눴다. 한 학생에게 두 표시가 겹쳐 뜨지 않는다 |
| 6자리 생년월일 세기 판단 보강 | 20YY 도 19YY 도 초등학생 나이가 아닐 때, **20YY 가 미래면 19YY 로 읽는다.** `850315` 를 2085년(아직 오지 않은 날)로 만들지 않기 위해서다 |
| 생년월일 구분자 인식 | 숫자만 모으면 `2017/3/5` 가 `201735` 라 여섯 자리가 되어 **20년 17월 35일**로 잘못 읽힌다. 구분자로 나뉜 세 토막을 먼저 본다 |
| 통합 검색에서 숫자만 친 경우 | 이름·주소를 뒤지지 않는다. `2` 로 찾을 때 주소에 `123` 이 든 집이 줄줄이 걸리면 안 된다. 숫자 1~2자리는 출석번호, 3자리 이상은 연락처로 본다 |

### 11.4 검토했지만 **바꾸지 않은** 것

| 항목 | 그대로 둔 이유 |
|---|---|
| `enrollments` 의 `UNIQUE(student_id, school_year)` | 이걸 풀면 "지금 몇 반인가"를 물을 때마다 최신 행을 골라야 하고, 가져오기로 생긴 중복이 눈에 안 띄며, 통계가 두 번 센다. 이력은 §11.1 의 사건 표로 푼다 |
| 학적과 졸업을 나눈 것 | 졸업은 학년도별 상태가 아니라 한 번 있는 사건이다. 나눠 두면 지난 학년도 명단을 열었을 때 6학년이 그해 모습(재학)으로 보이고, 화면 표시만 둘을 합치면 된다 |
| 형제를 학생 ID 쌍으로 두는 것 | 요구사항 §8 이 말한 그대로다. 문자열로 저장하면 진급 때 깨진다 |
| 확인 필요를 별도 표로 둔 것 | 한 학생에게 여러 개가 붙을 수 있고, 갈래가 늘어도 열이 늘지 않는다 |
| 반을 TEXT 로 둔 것 | `1`·`가람`이 함께 온다. 정렬은 SQL 에서 숫자 반 먼저, 그다음 가나다로 한다 |
| 주소 원본·정리값·판정 근거를 나눈 것 | 요구사항 §7 그대로다 |
